# Mobio backend, data, identity and service production-readiness review

Review date: 2026-10-01. Source snapshot: HEAD `9aa98e8cf5173fe7e3565f52cae37b14b9560785` plus the current working copy, including the changed dated BioPay approval. This is a read-only source review; only this report was written. Backend source was clean at the initial inventory, while unrelated client, design, native and landing-page changes existed and were preserved.

## Decision

**NO-GO for a general production launch on the evidence available.** Two source-confirmed authorization defects require priority correction: the organization-access helper treats every active member as a management user, and an always-available fixed store-review credential creates an ordinary consumer session. Tenant-helper callers include paid bus-booking confirmation, so direct booking-table write restrictions do not close the privilege path. Deployment of optional face recognition or automatic SMS allocation would require additional independent gates; their default-disabled policies are an appropriate safeguard and should remain closed until acceptance.

This review distinguishes confirmed implementation behavior, an incomplete implementation, and an external validation gate. A source defect does not establish a production incident. No real user identities, hosted rows, secrets, live payment references, deployed biometric images, or production endpoints were modified. Severity P1 means a high-priority release blocker; P2 means a material reliability, correctness or maintainability issue. The authorization-to-paid-confirmation path becomes critical when real paid inventory and affected tenant memberships are present.

## Findings

### BK-01 — P1 / confirmed defect: any active organization member inherits requested management permission

**Evidence:** [supabase/migrations/20260501090000_tenant_permissions_storage_realtime_hardening.sql:203-225](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260501090000_tenant_permissions_storage_realtime_hardening.sql:203) defines `can_access_organization(organization_id, permission)` as a platform permission OR any matching active membership. Its membership branch ignores both the requested permission and `org_role`. Roles explicitly include driver, member and viewer at lines 29-40. Lines 116-138 backfill the shared default organization and active memberships for historical profiles. The September live-identity rewrite strengthens the identity used by existing routines but does not change this authorization predicate. Agency upsert associates an agency with the profile/default organization at [supabase/migrations/20260615090000_transport_agency_admin_management.sql:78-80](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260615090000_transport_agency_admin_management.sql:78).

**Impact and reproduction:** A verified viewer/member/driver belonging to an organization can satisfy calls requesting that organization's management permission. This potentially crosses moderation, fleet, schedule, booking and passenger-data boundaries where RLS or RPCs call this helper. Critically, [supabase/migrations/20260929215434_mobio_hardening_transport_hold_receipt_integrity.sql:137-140](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260929215434_mobio_hardening_transport_hold_receipt_integrity.sql:137) uses it for `transport.bookings.manage`; lines 171-175 accept a caller-provided provider/reference as a paid receipt and lines 189-191 mark the booking confirmed/paid. EXECUTE is granted to `authenticated` at lines 198-200. A safe local reproduction uses synthetic roles: create a member or viewer in the booking organization, obtain a verified session, call the confirmation RPC for a held booking with a fresh invented reference, and check that it succeeds. No hosted exploit was attempted. Actual affected tenant counts and shared-organization use are an external gate.

**Remediation:** Separate membership from permission. Use an explicit reviewed organization-role/permission matrix, require an active organization, and deny unknown role/permission combinations. Keep paid confirmation limited to an authorized operator or service acting on independently trusted receipt evidence. Assess affected data and prior confirmation audits if this definition has been deployed.

**Acceptance:** Actual RLS and RPC tests for owner/admin/manager/driver/member/viewer/suspended/removed membership, unaffiliated users and cross-tenant users; ordinary members must fail management writes and confirmation. Hosted aggregate membership counts and `pg_get_functiondef` readback must match the corrected definition. Verify both allow and deny paths without relying on client-hidden buttons.

### BK-02 — P1 / confirmed defect: fixed store-review credentials produce unrestricted consumer identity

**Evidence:** [supabase/functions/_shared/play-review-login.ts:1-10](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/functions/_shared/play-review-login.ts:1) contains a fixed review phone and OTP; their literal values are deliberately not reproduced here. `send-login-otp/index.ts:60-70` passes the review predicate to integrity handling and bypasses normal send rate limits; line 159 chooses the fixed code; lines 180-185 skip delivery to the phone owner. `verify-login-otp/index.ts:333-337` accepts the review predicate when a stored hash does not match; lines 384-392 invoke the ordinary session creation path. That path creates/updates a normal WhatsApp-provider Auth identity and profile, then returns ordinary password-login sessions (`verify-login-otp/index.ts:129-145,153-169,177-219`). There is no deployment enable flag, expiry, restricted demo tenant or demo-only RLS scope in this path.

**Impact and reproduction:** Anyone knowing repository credentials can request and verify a review OTP without control of the phone and receive a regular consumer identity, including the supported passenger/driver role selection. It can interact with live marketplace functions according to normal permissions. The impact compounds BK-01 if the review identity receives an affected membership. This does not independently grant a platform administrator role. Existing tests intentionally preserve the fixed review contract, so passing tests do not prove safe isolation.

**Remediation:** Provide a dedicated, isolated review identity with synthetic data and a server-owned restricted permission/tenant scope. Require explicit time-bounded deployment configuration, avoid collisions with real phone identities, retain abuse limits, and revoke the review path after the store-review period. Restrict all backend paths, not only the visible review screen.

**Acceptance:** Review sessions must be unable to read or write real users' data, book/confirm real inventory, mutate moderation, create unrestricted accounts, or use normal private-media access. Normal authentication must never be acquired by the fixed review credential. Read back actual deployed configuration and identity metadata.

### BK-03 — P1 / validation gate: WhatsApp authorization is account metadata, while reusable Auth password and phone mutation paths need proof

**Evidence:** `verify-login-otp/index.ts:155-169` sets an Auth password and durable `provider=whatsapp_cloud_otp`; lines 204-208 obtain a session through `signInWithPassword`. [supabase/migrations/20260914214407_enforce_live_verified_database_identity.sql:28-35](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260914214407_enforce_live_verified_database_identity.sql:28) recognizes verified application identities from live Auth/account provider metadata, confirmed phone and the nonanonymous JWT flag. It does not require a per-session WhatsApp-verification record. Local [supabase/config.toml:213](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/config.toml:213) sets `secure_password_change=false` and lines 242-246 disable SMS signup but also disable SMS confirmations. This local config is not evidence of hosted configuration.

**Risk to validate:** An authenticated consumer may be able to set a known reusable Auth password and subsequently sign in directly without a new WhatsApp OTP, while retaining trusted account provider metadata. Phone-update behavior may similarly bypass the intended authoritative phone workflow under permissive Auth settings. Supabase explicitly supports authenticated password/phone updates; current upstream Auth behavior also checks bans and session existence, so this report does not claim that a revoked or banned requester necessarily passes `getUser`.

**Remediation/acceptance:** Reproduce against the exact isolated Auth version and intended hosted settings with synthetic users. Prove that direct password login, authenticated password changes, phone changes, alternate Auth methods and account recovery cannot manufacture a newly trusted application session or reassign confirmed phone authority. If they can, enforce a server-owned per-session OTP/lease proof or an equivalent supported Auth hook/control, and align identity consumers. Secure password change alone is not proof that password login always requires WhatsApp.

Primary references: [Supabase updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser), [local configuration semantics](https://supabase.com/docs/guides/local-development/cli/config), and [current upstream Auth user mutation implementation](https://raw.githubusercontent.com/supabase/auth/master/internal/api/user.go). Hosted behavior must be tested against its actual version.

### BK-04 — P1 / incomplete control: recent administrator reauthentication gate has no privileged callers

**Evidence:** [supabase/migrations/20260929215438_mobio_hardening_admin_session_leases.sql:90-105](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260929215438_mobio_hardening_admin_session_leases.sql:90) correctly requires live Auth, server/JWT admin-provider consistency, allowlisted confirmed phone and active idle/absolute lease. Lines 154-167 define `require_recent_admin_session()` for fresh authentication. Repository search across migration bodies finds its definition and ACLs but no privileged operation invoking it. For example, agency upsert requires a platform permission at [supabase/migrations/20260615090000_transport_agency_admin_management.sql:85](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260615090000_transport_agency_admin_management.sql:85), without the freshness gate.

**Impact:** A still-active administrator session can execute sensitive operations after the intended recent-auth window, within its longer idle/absolute session lifetime. This is not an absence of admin authentication or total lease enforcement; the incomplete part is operation-specific step-up.

**Remediation:** Inventory high-impact RPCs and enforce recent authentication inside each database transaction for role/allowlist changes, identity mutation, destructive operations and appropriate financial reconciliation. Expose a coherent reauthentication flow and preserve permitted lower-risk read operations.

**Acceptance:** With a lease that is idle-valid but older than the recent-auth limit, every classified high-impact operation must return `ADMIN_REAUTHENTICATION_REQUIRED`; successful fresh OTP must permit it. Test all overloads and indirect calls, not only the helper itself. Prove idle, absolute, revocation and banned-user denial separately.

### BK-05 — P1 / confirmed admission gap and P2 abuse-control gap: Maps accepts any Auth user and rate limits one process

**Evidence:** [supabase/functions/maps-gateway/index.ts:252-263](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/functions/maps-gateway/index.ts:252) requires only a successful `auth.getUser`. It does not enforce nonanonymous, confirmed-phone or trusted-provider admission used by [supabase/functions/_shared/app-user.ts:13-23](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/functions/_shared/app-user.ts:13). Its rate limiter is an in-memory Map at `maps-gateway/index.ts:56-84`, applied per user. Isolate restart or additional worker instances reset/divide that budget; it is not a global provider quota. Request JSON parsing and the Maps-specific client should also be included in the body/deadline review.

**Impact:** Bootstrap anonymous/unsupported Auth identities can potentially consume paid Places/Geocoding capabilities intended for verified users. A local per-isolate limit does not bound total production spend or sustained distributed traffic. The existence of Auth.getUser must not be described as no authentication; current upstream Auth rejects banned users and missing sessions, but explicit app-provider admission remains absent here.

**Remediation:** Reuse the verified-app admission contract and consistent active-session policy; introduce a durable abuse budget with provider-wide cost limits, bounded input fields/body, request deadlines and explicit safe degraded behavior. Preserve the intentional 410 `compute_route` response and approved external Maps links.

**Acceptance:** Anonymous bootstrap and unsupported-provider identities fail before provider fetch. Multi-isolate/restart and distributed-user tests demonstrate the budget; logs expose aggregate quota/latency/error data without addresses or raw searches. Provider console restrictions and costs must be read back separately.

### BK-06 — P1 / confirmed biometric moderation gap: recipient eligibility does not consult Auth moderation

**Evidence:** [supabase/migrations/20260920150000_biopay_face_shortcut.sql:276-284](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260920150000_biopay_face_shortcut.sql:276) resolves an active, nondeleted, consented, server-verified BioPay profile and an active receiving method, but does not join/check the payee's Auth `banned_until` or `deleted_at`. Its by-ID/session gate at lines 92-100 checks nonanonymous, confirmed phone, provider, session ownership and `not_after`, but omits moderation state and admin lease checks used by the general identity resolver. This feature was created after the September general live-identity rewrite. Service maintenance paths reuse these explicit recorded-owner/session checks.

**Impact:** Paused/removed face profiles are correctly excluded, but banning a user through Auth does not itself make their still-active face recipient unavailable in this resolution path. Recorded operations can also outlive a moderation transition unless all owner/session checks are aligned. Auth.getUser at the Edge boundary mitigates some current requester cases; the recipient path and service maintenance cannot be assumed covered by requester authentication.

**Remediation:** Define and implement one moderation-eligibility predicate for recipient discovery and recorded-owner service work, including soft deletion, bans and necessary admin leases. Apply it at result commit/reactivation, not only operation admission. Retain immediate SQL exclusion and delayed vector-removal verification.

**Acceptance:** Ban/soft-delete a synthetic recipient after enrollment and during pending insert/match/reactivation; no receiving method or identity is returned and no reactivation succeeds. Test requester session deletion/admin-lease expiry too. Do not reopen recognition merely because these local tests pass; calibration and deployment gates remain separate.

### BK-07 — P1 / confirmed operational lifecycle gap: processed SMS rows consume permanent intake capacity

**Evidence:** [supabase/migrations/20260929215436_mobio_hardening_durable_sms_intake.sql:13-24](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260929215436_mobio_hardening_durable_sms_intake.sql:13) defaults to 50,000 total rows, 10,000 per collector and 128 MiB payload capacity, with processing disabled. Lines 92-93 count every intake row and payload irrespective of completion status. Lines 113-114 reject new admission at the caps. Lines 176-177 explicitly preserve retained payloads and purge only nonsensitive budget rows. No controlled completed-payload retention/archival executor is supplied by this implementation.

**Impact:** Successful processing does not reclaim capacity, so sustained permitted traffic eventually prevents all new intake until an external maintenance action exists. Raw financial SMS and sender/timestamp data accumulate. Simply deleting intake rows can destroy durable deduplication and allow replay; simply raising caps postpones the same issue.

**Remediation:** Add an approved retention/archive lifecycle that distinguishes pending/manual-review/completed work, retains deduplication tombstones and required financial evidence, and safely reclaims personal payload capacity. Define measured thresholds, collector backpressure, alerts, restore behavior and operational ownership. Retention periods/bases require the applicable approved policy; this report does not invent them.

**Acceptance:** Fill and drain a synthetic small-cap queue, execute controlled retention, and prove new intake resumes while historical duplicate receipts cannot credit again. Restore/replay tests must preserve deduplication across archive and database restore. Test worker outage, lease expiry, poison messages, manual review and alert delivery. Device signatures establish possession of an enrolled collector key; independent institutional receipt/source trust still requires approved provider-format and device-control evidence before automatic allocation.

### BK-09 — P2 / confirmed transport correctness gaps; P1 operational activation gate

**Evidence:** Current hold logic at [supabase/migrations/20260929215434_mobio_hardening_transport_hold_receipt_integrity.sql:68-71](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/supabase/migrations/20260929215434_mobio_hardening_transport_hold_receipt_integrity.sql:68) accepts scheduled/boarding schedules when cutoff is absent or future; it does not itself require departure to remain in the future. Lines 107-112 store caller-provided `seat_numbers` without verifying cardinality, numeric range or exclusivity against existing bookings. The original booking table uses JSON seat numbers, not a unique per-schedule seat reservation relation. The latest durable expiry entry point exists at lines 202-223, but its comment explicitly requires operations to bind the approved scheduler. The old cancellation RPC remains relevant to paid cancellation/refund-pending states and needs the approved operational resolution process.

**Impact:** An incompletely maintained past schedule can accept a new hold. If numbered seats are offered, valid inventory counts alone do not prevent two bookings from containing the same numbered seat or inconsistent counts. Without deployed expiry scheduling/health, seats may remain held during low traffic. The source cannot establish actual provider settlement, late-payment handling or refund resolution.

**Remediation:** Enforce the approved departure/cutoff rule in the authoritative hold transaction. For numbered-seating products, validate and lock unique seat assignments; if the product is unassigned-seating only, reject unsupported numbered assignments. Bind the bounded expiry function to an approved scheduler and add age/overdue alerts. Preserve external payment/USSD scope; do not add unapproved in-app payment APIs.

**Acceptance:** Test past-departure/null-cutoff, count/seat mismatch, duplicate/overlapping seat selections, hold retry and expired holds under actual REST/RPC roles. Execute concurrent hold/confirm/cancel/expire scenarios and verify `available + held + confirmed = total` with nonnegative quantities. Receipt replay, wrong amount/currency/booking, late payment and manual exception paths must use trusted institutional evidence and approved operational acceptance.

### BK-11 — P1 / external gate and P2 architecture debt: effective database/API authority needs deployed catalog and forward-path proof

**Evidence:** The repository retains a long migration chronology, dynamic rewriting of existing routines and repeated source/migration bodies. The latest hardening files contain historical “not applied” source comments even when included as timestamped migrations. Local migration replay is useful but cannot establish the installed schema, effective overloads, grants, definer ownership, view behavior, extension versions or existing dirty production data. No globally applied default-function privilege policy was found in the inspected SQL; explicit per-function revokes exist extensively and must be audited rather than assuming any particular function is exposed.

**Impact:** A future `SECURITY DEFINER` helper or overlooked overload can reopen an API path despite otherwise correct RLS. Migration success in a new synthetic database does not prove forward safety from the actual hosted baseline, Auth compatibility, Storage/Realtime behavior or recovery integrity. RLS does not govern function EXECUTE authority by itself.

**Remediation:** Generate and verify an effective routine/ACL/policy/view catalog per deployment, covering all overloads and exposed schemas. Establish restrictive default privileges for future routines and prefer an internal/private schema where appropriate. Preserve already-applied migrations; do not squash or edit their history. Reduce duplicated forward-authoring material only with a canonical source, deterministic generation/hash checks and documented ownership. Update stale README/test comments against current checks.

**Acceptance:** Read back actual `pg_proc`, ACLs/default ACLs, policies/view security/owners, `pg_get_functiondef`, schema hashes and installed versions. Test anon, anonymous-authenticated, verified consumer, banned/deleted/revoked sessions, admin expired/fresh, organization roles and service roles through actual REST/RPC/Storage/Realtime. Rehearse a forward migration against a production-shaped anonymized clone and measured rollback/recovery plan. Supabase's official guidance explains function default access, explicit EXECUTE revocation and safe definer search paths: [database functions](https://supabase.com/docs/guides/database/functions), [API security](https://supabase.com/docs/guides/api/securing-your-api), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Positive controls worth preserving

- Live database identity joins Auth sessions and checks bans/soft deletion/expiry, replacing client-controlled anonymous ownership across established routines. This materially improves earlier M003/M004 concerns.
- The shared Edge admission helper uses server-side `getUser`, nonanonymous/confirmed-phone/provider checks and a bounded Auth timeout. Current upstream Auth validates banned status/session existence; blanket assertions that it accepts all revoked/banned users would be unsupported. See [upstream Auth admission](https://raw.githubusercontent.com/supabase/auth/master/internal/api/auth.go) and [session model](https://supabase.com/docs/guides/auth/sessions).
- Direct booking payment/status writes have been removed from ordinary clients. Receipt reuse is bound to one booking, hold expiry releases inventory durably, retry handling is explicit, and the sweeper is service-restricted. BK-01 concerns an indirect authorization predicate, not absence of all transaction controls.
- SMS collector admission binds RSA signatures to time/nonce/body digest, checks revocation and collector policy, bounds payloads, records immutable intake/deduplication and uses durable leases/retry budgets. Strict receipt parsing/allocation defaults fail closed.
- Admin leases live in a private schema, bind to actual sessions, enforce allowlisted confirmed phone, idle/absolute expiry and provider consistency; step-up integration remains BK-04.
- Face inference is private, size/pixel/capture bounded, model/version/checksum constrained, nonfinite vectors rejected, and clear busy/capture errors exist. Matching does not execute payment, face is not login, pause/removal immediately excludes profiles, and asynchronous cleanup is accounted for.
- Privacy workflow distinguishes requested/processing/retained/completed outcomes, requires per-category evidence and retention references, and cannot claim completed Auth deletion while sessions/users still exist. This is a solid evidence boundary awaiting its executor.
- Durable wallet-operation and notification journals, immutable operation identities, bounded discovery/pagination and updated chat delivery reduce retry/data-loss risk. Their local fixture validation still requires real operational/device/provider acceptance.
