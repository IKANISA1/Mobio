## Authorization regression evidence

The old schema allowed an ordinary active member with a consumer identity to call the real `rpc_confirm_bus_booking` for another passenger's synthetic held booking. The first regression failed with `real booking confirmation accepted ordinary member with consumer platform grant`. The fixture transaction rolled back. This was an isolated database demonstration, not an exercise against production accounts or payments.

The new migration was applied to that baseline through the local Supabase migration CLI. The new regression passed **121 assertions**, and every existing full-schema assertion group passed. A separate fresh replay of all **120 migrations** also passed the new regression and existing groups. The new tests use actual application functions/policies, live synthetic Auth users/sessions and the `authenticated` SQL role. They cover all six organization role labels, five existing management permission keys, retained own-organization/membership/booking reads, hidden foreign/private rows, real confirmation denial, exact trusted admin grants, full-admin fallback, grant/session-lease expiry and revocation, receipt creation and inventory conservation. Unchanged-booking checks also detect missing rows.

The correction preserves the current verified identity and admin lease resolvers, permission expiry, function signature/default and ACLs. Organization role labels do not acquire new management capabilities. Every existing management caller supplies a named permission; these callers now require the authority they request. Ordinary membership no longer reveals other members' roster rows through the platform-admin branch. The independent public catalog, booking-owner and assigned-driver policy branches remain in source.

The database runner disables cron execution before applying migrations and uses a uniquely named disposable project. Its fixtures and resources are removed afterward. It excludes PostgREST/Auth services: these results establish SQL-role/RLS/RPC behavior, not signed JWT issuance, HTTP admission, provider acceptance or hosted database parity. Representative production-data upgrade rehearsal, receipt verification, suspended-organization policy and complete private-catalog/assigned-driver journey acceptance remain separate work.
