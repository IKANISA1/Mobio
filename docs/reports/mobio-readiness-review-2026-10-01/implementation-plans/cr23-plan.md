# CR23 actual Auth acceptance and bounded correction plan

Prepared 2026-10-01, read-only. No runtime/configuration edits, Docker project creation/removal, account/provider calls, dependency changes or live credentials were used. The repository source freeze remains intact. CR23 is an unverified authority gate, not a demonstrated hosted exploit.

## Required result and current evidence

An Auth operation outside the approved WhatsApp OTP workflow must not create a newly trusted consumer/Admin session or reassign verified phone ownership. Refresh of an already proven session must keep working; logout, moderation, deletion/hold state, expiry and registered review isolation must remain effective. Successful Auth sign-in is not by itself Mobio application authorization.

## Smallest correction if the bypass is reproduced

Do not disable the Auth password grant globally: current consumer/Admin WhatsApp endpoints use it internally, and CR02 review factory plans an internal email/password exchange. Do not rely only on random hidden password, signup disabled, provider metadata, AMR=`password`, client ticket or a longer JWT/refresh policy. Those facts do not bind a new session to a consumed WhatsApp challenge; server and direct password grants share the same Auth method.

The minimum application-authority correction is a private **consumer WhatsApp session-proof table** plus service-only registration. Its key is actual `auth.sessions.id` with exact user UUID, consumed OTP reference/purpose, normalized verified phone/phone-confirmation snapshot, provider and server authentication time; retain revocation and any approved finite lifetime. Consumers do not gain invented Admin idle/recent policy. No client/service direct table writes; a narrowly granted SECURITY DEFINER RPC owns registration. OTP reference is unique across proof registrations so one challenge cannot authorize a second session, and session registration replay cannot renew/rebind it.

`rpc_register_app_whatsapp_session(user_id, session_id, otp_id)` (proposed name) must independently validate the exact real fresh session belongs to the live nonanonymous account, provider `whatsapp_cloud_otp`, consumed current `app_login` challenge matching the canonical phone and expected verified role, no registered/provider reviewer and no deletion/hold tombstone. Register only after the actual normal handler atomically claims the OTP and obtains Auth's real session, and before returning client tokens. Failure consumes the challenge and returns no admitted credentials; revoke the fresh Auth session via supported tested API. Never register consumer proof for Admin/review challenge purpose. Existing Admin lease and CR02 lease stay separate authorities.

Narrowly rewrite the installed `verified_app_user_id()` definition to require this exact proof for consumer provider and to require `verified_admin_user_id()` whenever stored provider is Admin, regardless of profile role. Preserve live/JWT/nonanonymous/phone checks, permanent CR02 review exclusion, owner/ACL/search path, existing Admin/consumer branches and applicable policies. Require proof snapshot matches current normalized phone and confirmation/binding version, so direct phone mutation invalidates the old application session. Refresh retains proof only when the actual session ID remains unchanged. New password/recovery/magic-link/anonymous-promoted sessions have no proof and remain untrusted even if durable provider metadata persists.

`_shared/app-user.ts` must validate exact bearer with Auth, then query the appropriate effective identity helper with that same bearer and reject error/null/mismatch before provider work. CR11/12's planned private `mobio_private.require_verified_interactive_session(user_id,session_id,requires_recent)` checks the same explicit consumer proof or existing exact Admin lease plus registry/tombstones under service-role calls; caller-bound review predicates alone are insufficient. Recipient eligibility separately checks live approved verified-phone binding and registry/moderation but must not require a payee to have an active interactive session.

If actual Auth phone mutation reassigns a confirmed phone, **session proof alone closes new sessions but does not make the durable phone-owner directory trustworthy**. Add a small private durable WhatsApp identity-binding record (user UUID, unique canonical verified phone, binding generation, proof time/reference), updated only by the approved verified-phone workflow. `_mobio_verified_phone_owner` must error on Auth/current-binding mismatch instead of returning null or trusting a newly auto-confirmed Auth phone; null means callers may provision a replacement. Ordinary OTP login must not silently adopt a changed phone onto an existing UUID. Phone changes need an explicitly authorized WhatsApp/recovery flow and independent proof, or fail closed for recovery. This is conditional on the causal phone test and approved product phone-change contract, not a speculative new phone-management feature.

Initial legacy migration should not fabricate proofs for existing password sessions. Fail closed and require a new WhatsApp login unless an independently evidenced session-specific transition is approved. A legacy account's verified phone binding may be seeded only from reconciled historical server-authored WhatsApp evidence; ambiguous/mutated/no-evidence accounts require recovery. Expiring OTP cleanup cannot delete durable phone authority/proof: store immutable relevant snapshots/reference independently rather than joining a short-lived `otp_codes` row on every future read. Deletion/restore/hold state from the CR10 plan revokes registration/authority without becoming an invented permanent phone ban; the permanent review UUID tombstone remains separate.

An Auth password-verification or access-token hook is an optional additional boundary only after exact engine/plan support and fresh/refresh/recovery behavior are demonstrated. It is not the minimal first correction: a blanket password rejection breaks current OTP-issued password exchange, and a token hook runs during issuance before the endpoint's post-issuance registration. Do not propose a hook that assumes an unissued session has already been registered. [Official password-verification hook contract](https://supabase.com/docs/guides/auth/auth-hooks/password-verification-hook).
