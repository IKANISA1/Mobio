## Recommended server query contract

Use a new, explicitly named page RPC rather than changing the return type of the old four-argument RPC. Proposed `rpc_admin_users_page(p_role text, p_search text, p_sort text, p_limit integer, p_snapshot_id uuid, p_offset integer) RETURNS jsonb`, with defaults compatible with the current first page. Keep the old read RPC for compatibility; its clients must not claim an exact count or global local sort.

1. Verify current admin identity/live lease and `admin.users.read` on every request. Reads do not require recent authentication. Normalize blank role/search to null; allow only the three existing roles, five existing sort keys and current page sizes 10/25/50. Reject unknown values and invalid offsets instead of interpolating SQL. Preserve search coverage over name, display name, phone and six-digit member ID.
2. Apply filters, deterministic ordering and the count in the server before pagination. Ordering tuples are: online `(is_online DESC, role::text ASC, lower(name) ASC, id ASC)`; A-Z `(lower(name) ASC, id ASC)`; Z-A `(lower(name) DESC, id ASC)`; role `(role::text ASC, lower(name) ASC, id ASC)`; newest `(created_at DESC NULLS LAST, lower(name) ASC, id ASC)`. Spell out null handling/collation in SQL and test it; lexical role order matches current intended behavior, not enum declaration order. Preserve the current wire representation/name fallback.
3. For the required concurrency guarantee, first page captures immutable ordered row payloads and total in one SQL statement into a short-lived, server-private query snapshot. Subsequent pages use an opaque snapshot ID plus validated offset; no duplicates/skips or reshuffling inside that query, even when names, online state, roles or profile membership change. Owner is the verified admin UUID **and exact Auth session ID**. Bind normalized filters/sort/page size; recheck permission/lease each page, reject mismatched handles, and enforce server TTL/resource limits with cleanup. No direct REST grants to snapshot storage. Returning IDs while rereading changed sort fields would not prove the displayed ordering; preserve the projected row values too.
4. Return validated `{snapshot_id, as_of, expires_at, total_exact, rows, offset, page_size, has_next_page}`. An expired/invalid snapshot is a read error; start a newly identified query at page zero through explicit refresh, with clear feedback. Filters/sort/page-size changes also start a new snapshot at zero; ordinary next/previous uses the same one. Existing query revision and account/session guards reject old responses. Refresh after a role operation obtains current data; it cannot erase the operation's recipient ledger.

A UUID tie-breaker plus live offset is insufficient under insert/delete. Keyset pagination alone is also insufficient for all five sorts: role/name/online keys are mutable. A server snapshot is the smallest uniform contract here that actually satisfies the stated concurrent-write acceptance without silently changing the result mid-query. Its TTL, storage budget and realistic-volume cost must be measured in the implementation fixture; no production performance claim is made by this plan.

Count labels must reflect their evidence. With `total_exact`, display “N matching members · as of <query time>”; pagination may say “x-y of N”. Until that contract is present, use “At least N matching members” only where rows plus sentinel prove the bound, otherwise “N members on this page”; use “x-y · more results available”, with Next driven by `hasNextPage`, not a fictional exact maximum. Never infer a global total from a later empty offset page. All page metrics explicitly say “This page”; Online reflects the query time. Extend shared `AdminPaginationBar` with optional count semantics/has-next parameters whose defaults preserve its other callers, or introduce a users-only wrapper; do not relabel every admin list accidentally.

## Reviewed role-change and receipt contract

### Freeze and review before any write

Role chips open a review of a frozen plan; they never call a mutation themselves. Each reviewed entry contains internal target UUID, operator-facing six-digit member ID/name, observed old role, requested role and skip reason for self/same-role. Show eligible and skipped counts and expected effect: Driver enables the driver role flag; Passenger removes it; Admin changes the profile role and may confer existing platform permissions **when the existing trusted admin sign-in/allowlist conditions hold**. Changing a profile role does not register an admin session or add an allowlist entry. No invented privilege catalogue or permission.

Cancel leaves selection/role/query unchanged and performs zero writes. Confirm is owner/session/action-token bound, disabled during submission, and submits that exact plan rather than recomputing live selection. Selection/clear/filter changes cannot silently change reviewed recipients. A changed/disposed account cancels presentation and further dispatch. Single-user role chips should use the same review path for one target; preserve the current self-role lock. Keep unresolved recipient outcomes independently from the visible page and selection.

### Minimal reliable server mutation/read receipt

Add `rpc_admin_change_user_role(p_user_id uuid, p_expected_role text, p_role text, p_operation_id uuid) RETURNS jsonb`. Preserve the old RPC as the actual existing mutation path. The wrapper calls the shared recent-auth requirement, checks existing `admin.users.manage`, validates existing roles/self rules, locks the actual target row, rejects a missing target or role mismatch **before** calling the existing freshness-wrapped role RPC, and records a private durable per-operation receipt in the same transaction. The lock ensures the reviewed old role still applies and avoids auditing a nonexistent target as success.

Bind operation ID to verified actor, target, expected role and requested role. A uniqueness check cannot accept the same key with altered arguments. Receipt reports the proven before/after role, target, actor, operation ID and commit time, and matches the audited change. Private receipt writes are server-only; no client table privileges. New mutation routines explicitly retain freshness, live verified identity and exact existing permission; service does not gain a new bypass. An exact duplicate may return its original receipt only after current authority checks; the client does not automatically replay it.

Add `rpc_admin_role_change_status(p_operation_id uuid)` as a lease/`admin.users.manage` protected **read** for the same actor, so reconciliation itself need not require freshness. It returns the committed receipt or an explicitly unconfirmed status; it must not leak another actor's operations. This distinction matters: seeing the current profile role alone does not prove this operation committed, and absence of a receipt while the original request is still running does not prove failure. An unknown result stays unknown until a receipt proves it or a terminal server result proves rejection; never automatically resubmit unknown work. If terminal rejection is not persisted by the chosen implementation, retain unknown honestly instead of asserting that an absent receipt proves no change.

### Per-recipient outcomes and freshness

Model recipients as `skipped`, `not_started`, `submitting`, `confirmed`, `known_rejected`, or `unknown`. Confirmed requires a valid target/operation/before-after receipt. A lost/timeout/5xx response is unknown; a malformed post-mutation response is also unknown because validation failure cannot undo a commit. Exact SQL validation/permission/conflict and freshness denials are known rejections. A list refresh failure is independent from the recipient outcomes. Display recipient name/member ID, old/requested role, status and available safe action; aggregate numbers must include unknown and not-started counts, not a single “success” banner.

Dispatch sequentially within this currently page-scoped batch. This preserves a bounded target set, stops further recipients after a freshness/authorization or unknown result, and marks the remainder not started; confirmed earlier recipients remain confirmed. Known target-specific validation/conflict can be recorded and processing can continue. Duplicate Confirm cannot start a second dispatch. Only an explicit new review after reconciliation may retry known rejected/unstarted recipients; uncertain operations remain blocked from replay.

Reuse the current client boundaries: `AdminBaseService.mutate` already calls `AdminMutationGuard.run`; `AppExceptionMapper` maps **exact** SQLSTATE42501/message `ADMIN_REAUTHENTICATION_REQUIRED` to `AdminReauthenticationRequiredException`. The guard fences only the owner/exact session captured for the rejected request via `AdminSessionGuard.rejectSession`; status/touch/refresh cannot restore that session. Use the existing `/admin-auth` screen and `OtpService.sendOtp/verifyOtp` (`/send-otp`, `/verify-otp`) to obtain a new trusted admin session. CR03's `require_recent_admin_session()` remains server authority with immutable authentication time, 300-second policy, future-time protection, live lease and original permissions. Do not write a new OTP flow, add a client freshness grant, or replay the reviewed batch after login. Reauthentication invalidates the old reviewed plan; a new plan can include only explicitly reconciled eligible entries.
