## Current result and exact remaining gap

`supabase/migrations/20260929215442_mobio_hardening_privacy_request_workflow.sql` implements private policy, requests, evidence and actions; authenticated owner-only intake/status/cancel; service-only configure/worklist/fulfil; admin aggregate health. Both intake and processing start disabled. `supabase/functions/_shared/privacy-request.ts` forwards the captured caller bearer to SQL without service elevation; `lib/features/privacy/data/privacy_service.dart` retains account/session fences and unknown-outcome recovery. The screen correctly says submission is a request, not immediate erasure.

Existing controls to retain: notice/approval reference, approved inventory/plan hashes, fresh originating session, one active request per owner, bounded submission frequency, immutable action IDs/input hashes, compare-and-swap revision, cancellation only before processing starts, append-only evidence revisions, explicit block codes and service-only fulfillment. A retained category requires a future explicit `retention_until` and `basis_reference`. Auth/sessions must be deleted; identifiable privacy case records must be retained with an approved exception. Do not weaken those requirements or invent a period/basis to enable completion.

There are **no privacy processor, execution-task, worker-lease or legal-hold tables/adapters** in the current source. `rpc_privacy_fulfil` records an operator's separately executed work; it never performs erasure. Its completion probes only actual Auth-user/session absence, accepts hashes for other categories, and requires all ten category records. `scripts/privacy/verify_completion_manifest.py` checks safe local paths, hashes, request/subject/category bindings and retention consistency; its output explicitly says `provider_deletion_independently_verified=false`. A hash-valid operator assertion is not a processor deletion receipt. `PrivacyHealthCard` correctly requires `automatic_erasure_implemented=false` today.

Reuse evidence, with limits: root's existing `build/qa/readiness-20261001/goal/cr02/run-99112/catalogue.json` reports 122 replayed migrations/89 restricted relations, and `helper-contract-after.json` confirms preserved resolver/hook owners, ACLs and empty search paths. They do **not** export effective FKs, Storage contents, per-store subject data or external processors. The table map below is a static migration/source trace, not a full installed-schema/data export. No deployed retention setting, processor contract or backup snapshot was examined.

### Concrete deletion-order hazards

- `mobio_private.wallet_operations.owner_id` references Auth with `ON DELETE RESTRICT`; `token_redemption_requests.admin_profile_id`/`wallet_transfer_id` also restrict deletion. Provider-route tester/reviewer profile references have no deletion action. Effective retained-record representation/FKs need an explicit migration before Auth/profile deletion; retain required records without a live account, not a hidden active Auth row or new cascade. Current completion explicitly rejects any remaining Auth row.
- Wallet transfers/ledger, bookings/payments, chats and profile activity have CASCADE edges that can remove counterparty/evidence rows or change seat reconciliation if blindly triggered. SET NULL preserves copied names, phone numbers, JSON/notes and ticket references. Discover both kinds in the installed catalogue and prove them in real fixtures.
- Face revisions cascade with profiles, but cleanup only holds explicit vector/model IDs. Capture/enqueue IDs durably before removing the source rows; deletion receipts and cancellation fences must survive Auth/profile removal. A provider timeout/late asynchronous insert cannot turn into a forgotten orphan.

## Minimal execution design, without enabling processing

Use the existing privacy case/state machine; do not introduce a second request product or a general deletion endpoint. Add one forward migration for private execution controls, one server worker with a fixed adapter allowlist and maintained receipt/manifest verification. All controls remain disabled by default until approved inventory, scoped plan, retention/hold decisions and adapter evidence exist.

1. **Approved subject plan:** create an immutable versioned manifest from the request's server-resolved owner, exact environment/account, store selectors, object/vector IDs, category dispositions and approval references. Hash inventory/plan and reject mismatch/changed environment. Unknown relation/processor/cascade or ambiguous ownership blocks `inventory_incomplete`/`identity_review`. No caller table names, SQL, bucket-wide prefix or arbitrary provider URL is executable input.
2. **Retention/holds:** add private `privacy_holds` with scoped categories/object selectors, basis/approval reference, status and review responsibility. Every destructive adapter rechecks the current hold generation before action/acknowledgment. No approved period means `retention_review`, not a fabricated date. Preserve the current future explicit retention-until completion rule; an open-ended/unknown hold cannot be disguised as a bounded approved exception. Releasing or changing a hold requires a reviewed plan revision.
3. **Durable task leases:** add `privacy_execution_tasks` and append-only `privacy_task_receipts`, bound to request, plan/inventory hashes, processor/adapter version, deterministic task/operation ID and generation. State distinguishes queued/leased/retry/unknown/blocked/verified/retained. Claim via service-only SKIP LOCKED/fenced lease; stale workers cannot acknowledge after expiry, hold or plan change. Record bounded attempts/next-attempt/error codes and manual blocked follow-up; do not log subject payloads. Reuse existing lease patterns from push/SMS rather than a new queue platform.
4. **Access/restore fence first:** durable private `privacy_erasure_tombstones` without cascading Auth FK, before destructive external work. Freeze discovery, Face activation, pending sends and consumer writes; revoke all subject Auth/admin leases and stop proof issuance. Every relevant live resolver, CR23 session-proof registrar, parameterized service actor helper and signup/profile materializer must check the tombstone. Fence old UUID resurrection/restored jobs, not a newly invented permanent phone-number ban. Re-registration policy/identity mapping needs approval. The tombstone itself is retained security metadata with an explicit approved legal treatment; no retention period is invented here.
5. **Bounded adapters:** capture target identifiers; cancel/fence pending work; process SQL/Storage/vector/provider tasks independently; preserve approved financial/safety/shared records through reviewed redaction/detachment; supported Auth removal runs after relevant FK prerequisites, followed by actual absence/old-credential checks. Auth deletion is neither a prerequisite for provider-ID inventory nor permission to delete counterparty records. Device cleanup is separately acknowledged when possible. Secrets stay in worker environment; user/admin clients cannot invoke deletion or choose targets. Existing service-only fulfillment control is retained.
6. **Trustworthy receipts/completion:** each receipt binds environment, subject/request, plan version, exact target-set hash/count, adapter version, operation/provider request ID, observed time, terminal result and independent postcondition probe. A deletion 202/accepted response is pending; absence/terminal completion is required where supported. Lost responses remain unknown and are reconciled by the same operation ID; do not resend an unconfirmed non-idempotent operation. Retained receipts also bind the exact approved basis/until and restricted-access check. Provider receipts must not expose full phone/object keys to clients.
7. **Completion gate:** strengthen the existing service completion action to require all approved task dispositions and verified category coverage, no active lease/unknown/retry/due hold, current receipt/manifest hash and live SQL/Auth/Storage/vector postconditions. Existing ten category evidence remains; per-store receipts cannot be replaced by ten arbitrary hashes. Keep manual operator attestation labelled as such, with accountable evidence, instead of presenting it as independent provider verification. Backups/processors/local copies with unresolved evidence block or have explicit approved retained/not-applicable dispositions. Completion remains `completed_with_retention` where the required case/security records survive.

CR02 permanent review tombstones must remain excluded after Auth deletion, provider alteration and restore. Do not delete the review registry or conflate a registered synthetic review identity with an ordinary consumer deletion workflow; current verified-app admission rejects it. CR23's eventual session-specific consumer WhatsApp proof is a dependency for reliable revocation/reenablement prevention, and CR11's parameterized service-target admission must consume the same fence. Root owns common helper/OTP write coordination. Privacy-only worker credentials do not manufacture new interactive permissions or one of CR03's service bypasses.
