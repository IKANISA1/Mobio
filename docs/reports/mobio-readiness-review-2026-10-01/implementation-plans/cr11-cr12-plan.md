# CR11 / CR12: Face and Maps authority preparation

Read-only preparation, 2026-10-01. This note is the only write. CR03 remains frozen; its migration/test hashes still match the reported freeze. No runtime/test/migration change, provider call, hosted readback, test run or build occurred. Root retains combined verification/build ownership.

## Required outcome and verified boundaries

Face requester/session admission and recipient eligibility must reject bans, deletion, permanent review identities and expired authority, while preserving the approved same-face receiving-method workflow and legitimate maintenance callers. Maps must admit only verified non-review interactive sessions and enforce a shared quota before expensive Places/Geocoding calls. `compute_route` remains 410. No Routes/ETA/distance/polyline/dispatch capability is proposed.

### Route/config evidence limits

`supabase/config.toml` explicitly sets `verify_jwt = false` for both Face facades. `docs/operations/face-ussd-runbook.md` explains in-handler exact-bearer Auth+SQL checks for interactive calls and the dedicated secret for maintenance. `cloudflare/face-service/wrangler.jsonc` exposes a workers.dev endpoint, with one private inference container, model-specific Vectorize binding and observability disabled. Its handler authenticates every request with a constant-time server bearer-secret comparison; it receives opaque IDs/embeddings and has no receiving-number database. It is not the place to add user JWT or recipient selection authority.

Maps has no explicit function section in the local Supabase config. The client invokes the `maps-gateway` slug from `lib/core/location/places_service.dart`. Local configuration and the runbook do not prove hosted gateway flags or deployed artifact identity; read back those settings as a later release action. Do not disable an existing gateway check as a shortcut. Any chosen explicit config must match the actual signed-token mode and retained in-handler authority tests. No live route/secret/config mutation is part of this plan.

## Smallest shared interactive identity change

Coordinate one owner with CR02 before writing `_shared/app-user.ts`; the CR02 agent already plans caller-bearer SQL verification there. Do not create two competing authentication flows.

After the existing exact-token Auth check, use that same bearer with a bounded caller client to read a narrow `rpc_verified_interactive_session()` returning `{user_id, session_id}`. The RPC requires SQL request role authenticated, `verified_app_user_id()` nonnull and exact live session. It additionally requires `verified_admin_user_id()` to equal that user when the trusted stored provider is `admin_whatsapp_otp`; ordinary app ownership must not bypass the admin idle/absolute/allowlist policy. Reuse the installed CR02 exclusions in both verified resolvers. Compare the returned owner/session to the Auth-validated token; a null/error/malformed/mismatched response fails closed before a provider call. No service key or caller-submitted user/session argument is used for this admission RPC. Ordinary identity reads and Maps access require an active lease for admin sessions, not the separate recent-auth timestamp.

Keep `AppUser` as the same `{id, sessionId}` type. This benefits Face health/status before any inference and gives Maps the intended common admission. Auth/JWT signatures are checked by real Auth and PostgREST; merely decoding a token never authenticates it. A service-key token alone is not an interactive user. Maps currently has no supported server-only admission branch, so do not invent a bypass; Face's legitimate secret/service callers are separately retained below.

Maps currently has a local `HttpError(status,message)` class distinct from the common `HttpError(message,status)`. If it reuses `requireAppUser`, explicitly translate/catch the shared error type so a verified-identity 401/403 is not accidentally returned as 500. Keep public responses and telemetry free of tokens/phone numbers.

## CR11 service-side session and recipient authority

### Parameterized session check under service authority

Add a private, owner/session-parameterized internal helper named `mobio_private.require_verified_interactive_session(p_user_id uuid, p_session_id uuid, p_requires_recent boolean DEFAULT false) RETURNS void`; no direct grants to public/anon/authenticated/service_role. Public Face entry routines retain their explicit existing service-role check and invoke it as owner. Preserve old `fn_biopay_face_session(uuid,uuid)` signature/ACL as a service-only wrapper, so current callers cannot bypass the strengthened base check.

The helper must check real Auth user/session rows: nonnull exact UUIDs; stored nonanonymous confirmed WhatsApp provider; `deleted_at IS NULL`; `banned_until IS NULL OR <= statement_timestamp()`; session belongs to that owner and `not_after` is null/future; provider is one of the two existing trusted providers; explicit `NOT EXISTS` for `mobio_private.store_review_principals(user_id)` plus stored `store_review` provider denial. The permanent exclusion is essential even after provider/role changes. Caller-bound `is_store_review_principal()` cannot inspect the target while the request JWT belongs to service-role; the CR02 owner confirmed that no parameterized helper already exists.

For stored admin provider, also require the existing active phone allowlist and exact unrevoked admin lease with future idle/absolute deadlines. If `p_requires_recent`, require `authenticated_at <= statement_timestamp()` and strictly newer than the shared policy's recent window (currently 300 seconds), preserving the CR03 boundary/future-time protection. Never refresh a lease or authentication time here. Hold appropriate shared authority locks through activation/resolve commit so an Auth soft delete/ban update cannot silently interleave after its eligibility check.

Recent authentication is action-specific: reserve enroll/resolve and Face mutation authority actions `begin_enroll`, `activate`, `pause`, `remove`, `resume`, `change_method`, `fail_enroll`, `resolve`, `handoff` require freshness **for an admin-provider interactive owner**. Read `status`/`operation` requires a live verified session/lease only; `status`'s later activation has its own freshness check. Consumer WhatsApp users retain their existing self-service authority; no admin permissions are added to the consumer workflow. The service activation of a pending admin enrollment rechecks the originating recorded admin session/freshness; it is not a new interactive bypass. After expiry it cannot activate, but cleanup must still remove orphan vectors.

Use exact SQLSTATE42501/message `ADMIN_REAUTHENTICATION_REQUIRED` for a live stale admin and preserve `BIOPAY_SESSION_INVALID` for invalid/banned/deleted/revoked/expired base authority. `_shared/biopay-authority.ts` currently recognizes only the latter, mapping it to `AUTH_EXPIRED`; add a precise freshness mapping rather than treating it as generic database failure or unknown. The app's Face service currently needs a focused typed propagation check against the existing admin reauth boundary; root coordinates any client change. No OTP protocol or automatic replay is added. Keep CR03's frozen helper/migration untouched.

### Recipient account eligibility without login requirement

Add a private Boolean `mobio_private.biopay_face_recipient_is_eligible(p_user_id uuid)` using current Auth state: real nonanonymous confirmed trusted WhatsApp account, not deleted/banned and not permanently registered as review. Apply it when the top vector resolves its current recipient, before choosing the method or constructing USSD, including cached matched operations. Lock the corresponding Auth row with the existing profile/method/route shared locks as appropriate. A denied top recipient returns the existing generic `recipient_unavailable`; never select a lower unrelated candidate or expose the ban/deletion reason.

Do **not** require a recipient Auth session, active admin lease or recent admin login. An opted-in active receiving recipient can be signed out while a payer scans them. The active lease/freshness rule belongs to the interactive requester and originating pending enrollment, not to recipient discovery. Preserve same-owner duplicate candidate grouping/margin policy, previous active enrollment during replacement, chosen receiving number B differing from login number A, method edits without recapture, consent removal/pause/remove, no payer enrollment, no liveness, no amount and no extra application review. Retain explicit model/version and current-pointer checks; no AWS fallback.

`handoff` records that the dialer opened; it is not a new authorization/pre-dial review and cannot retract a code already returned to a device. Prove eligibility when SQL returns a route and on every fresh/cached resolve, with the existing short expiry. Do not claim that a later ban can revoke a previously delivered external USSD string. Legitimate provider `/health`, `/query`, `/enroll`, `/searchable`, `/delete`, `/absent` server-secret requests and secret-driven cleanup continue unchanged; private Worker auth does not need user JWTs.

## CR12 durable quota before Google access

Replace the isolate-local admission Map with one server-private SQL bucket per verified owner UUID, preserving the existing allowance of 100 requests per five-minute window. Session IDs, client session tokens and isolate IDs are not bucket keys; signing in again cannot reset an account budget. Enforce on all five allowed actions before cache/provider access, keeping cache hits charged like the existing behavior. Validate supported action/body first so unsupported/invalid input and `compute_route` do not consume protected provider budget; for an admitted interactive user `compute_route` still returns 410 with zero counter increment/provider calls, even when their quota is exhausted.

Proposed `rpc_consume_maps_quota(p_action text) RETURNS jsonb` runs with the caller's JWT, checks live verified non-review identity and admin active lease itself, validates the five-action allowlist, and atomically inserts/locks/updates a private bucket using server time. Return `{allowed, remaining, retry_after_seconds, window_ends_at}`; derive the retry delay from the actual boundary and add HTTP `Retry-After` for a quota denial. Do not raise after an increment expecting it to persist: exceptions roll back transactions. A conditional atomic increment must admit exactly the configured count under concurrency and return denied afterward without a reset. No direct table grants, client-supplied owner/window/max, service-role shortcut or local fallback. Bound expiry cleanup without deleting an in-window budget.

The common identity RPC rejects before counting; the quota RPC rechecks authority in its own transaction. A failed identity or counter call returns a bounded 401/403/503 with **zero Google calls**. Do not refund a successfully acquired slot after Google timeout/5xx because the provider may have accepted/billed it. Retain current no-server-retry 8-second/500KB bounds, Rwanda-only outputs and server-only key. Existing Flutter Places retries are bounded and skip all 4xx; each 5xx/timeout retry acquires its own slot. No new provider or dependency is required. This is a durable account quota, not proof of a project-wide Google spending ceiling; retain provider-key project restrictions/billing controls as a separate release gate.
