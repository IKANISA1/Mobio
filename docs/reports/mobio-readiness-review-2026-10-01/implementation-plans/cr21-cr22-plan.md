# CR21/CR22 — bounded receipt intake and transport inventory

Read-only plan prepared on 2026-10-01 during the frozen source/build window. No runtime, test, Kotlin, old migration, scheduler, provider or production changes were made. No tests/builds were run for this investigation. Existing frozen CR03/05/06 work and other dirty changes must remain intact; implement future fixes as a coherent owned batch and additive migrations.

## Product boundaries

The consumer app remains an external-payment assistant under `docs/product/biopay_ussd_aws_reactivation_scope_2026-06-12.md`; that approval explicitly excludes consumer SMS inbox ingestion, PIN capture and automatic in-app settlement. CR21 concerns the already separate `apps/momobio_sms_bridge` institutional receipt collector and its server intake, not permission to add consumer SMS APIs or a public payment activity screen. Its README limits collection to new configured institutional notifications. `docs/operations/collector-acceptance-2026-09-28.md` is an unexecuted approval/recovery procedure, not evidence of approved operator formats, legal retention periods, fleet rollout or payment success.

`docs/product/public_transport_tracking_booking_scope_2026-06-08.md` approves transport schedules, seat quantities and conditional seat numbers **when a seat map exists**, short holds and booking-specific confirmation. This does not approve dispatch, Mobio route computation, automatic consumer settlement or a new refund implementation. Preserve the existing provider/agency confirmation authority and external Google Maps handoff. No new UI is required by either minimal fix; any later UI must keep Mobio identity and the sole Revolut design authority.

## CR21 — minimal additive implementation

1. Add an operator-controlled processed-payload retention policy and a compact **private intake tombstone** keyed by `(collector_id,message_hash)`. Retain original admission ID, canonical normalized payload fingerprint, receive/completion time, final status and durable receipt reference; no raw SMS. Fingerprint the normalized raw/sender/receive tuple with unambiguous encoding so a same-hash/different-payload retry remains a conflict. Keep tombstones RLS protected and reachable only through the existing service-controlled admission/reclamation RPCs. Do not weaken the independent `sms_hash`/provider-reference/invoice financial guards.

2. Add one bounded service-only reclaim RPC with the **same intake advisory lock** as admission/claim/completion. It selects only policy-approved, sufficiently old, definitively processed rows with verified durable completion/receipt references and no retention hold. Atomically insert/verify the tombstone **before** removing the raw intake row. A failure rolls back both. Never reclaim queued, retry, processing, review, stale/unknown, held evidence or uncertain allocation. Legal/evidentiary raw retention can remain in its existing controlled source or approved archive; if archival is required, verified archival receipt and policy reference precede deletion. Do not invent a retention period or blindly purge receipt tables. Enable execution only with an approved policy; test fixtures may use an explicit synthetic policy.

3. Admission checks active rows and tombstones before capacity; a matching tombstone returns the existing v1 `duplicate` response with stable `admission_id`, `admission_status: processed`, `review_required: false`. Preserve `INTAKE_HASH_CONFLICT` and the current all-or-nothing batch transaction, including mixed duplicate/new batches. Count retained raw intake rows/bytes against existing caps after reclamation; monitor compact tombstone storage separately. Tombstone expiry cannot be shorter than the approved replay/restore horizon and must not become a hidden path to recredit. If that horizon is unknown, retain the guard and expose the unresolved retention-policy gate rather than silently age it out.

4. Extend existing health/operations metrics with total/per-collector retained payload use, processed rows eligible for reclaim, held/uncertain rows, capacity headroom, last reclaim result/time and oldest retained backlog, without raw receipt/PII logging. Keep 503 + Retry-After backpressure; retain local evidence. Bind reclaim to an owned protected scheduler independently of the processing kill switch. Existing `scripts/operations/run_sms_intake_worker.py` and its once-per-minute systemd timer are templates for bounded protected triggering, not proof they are deployed. Do not couple reclamation to parser success or silently enable allocation.

5. Add an injectable monotonic **per-request deadline and cancellation handle** to the existing upload transport; retain current endpoint/signature/response and acknowledgement contracts. Account for connect, exact signed-body write, headers and complete bounded-body read. Clamp phase waits to remaining duration; enforce a real abort path for blocked I/O with a watchdog/cancellation handle that closes owned streams/disconnects the active connection. Check terminal state before queue acknowledgement, before each next chunk and before starting another connection. Worker `onStopped` and foreground executor destruction cancel their own active handle. A notice/permission pause stops further chunks/syncs; the already-running chunk may finish according to the current disclosure, and an already validated durable server acknowledgement remains safely recordable.

6. Keep the OS lease until the sender is actually stopped or completes. Preserve partial known acknowledgements already committed before a later timeout/cancellation; retain the unresolved chunk and any later chunks, return a sanitized typed outcome, and reuse persisted backoff. Do not release the lease early while an abandoned network thread can still send or acknowledge. Use a bounded overall sync/chunk count as well, so many individually bounded requests cannot monopolize the lease. No new production transport dependency is assumed; actual Android cancellation must be proven, not inferred from `disconnect` or a future timeout.

## CR22 — minimal implementation without feature expansion

1. Add a forward migration that locks the schedule and samples a current `timestamptz` **after lock acquisition**, requiring finite future departure and current scheduled/boarding status. Treat null cutoff as departure; a later cutoff cannot extend admission beyond departure. Admit only before `min(departure_at, non-null booking_cutoff_at)`. Apply the same future-departure/cutoff predicate to schedule search. Preserve cutoff as a **new-hold admission** rule: do not silently turn it into a deadline for an already admitted payment. Cap the existing ten-minute hold at departure; an earlier confirmation deadline requires evidence of the approved policy. Test exact-boundary and non-UTC sessions; do not use a timestamp-without-zone conversion or a pre-lock timestamp as authority.

2. Keep the existing RPC signature/default and support only `[]` assignments in the current quantity-only journey; reject null/malformed/non-array/non-empty seat assignments before inventory writes. A Dart service guard can surface the same supported contract before an HTTP call, but SQL remains authoritative. Do not remove `seatNumbers` from historical models or clear old assignments. Preflight existing active numbered bookings/seat maps and inventory drift; retain them for controlled resolution and stop the affected unsupported schedule from issuing new assignments. Do not guess a migration that overwrites approved deployed data.

3. If a later verified approved deployment actually offers numbered maps, that is a different admitted branch: require exactly `seat_count` distinct canonical seat IDs from the schedule's **validated seat map**, and reserve each uniquely across active held/confirmed bookings within the same schedule transaction. Expired/cancelled assignments must release exactly once; equivalent retries compare a normalized seat set. Count-only inventory with an unchecked JSON array cannot establish exclusivity. Do not implement this branch or a new selector merely because the historical schema has fields for it.

4. Preserve existing equivalent-hold idempotency and provider receipt uniqueness. Use one documented lock order for all affected hold/confirm/cancel/expire mutations; serialize the schedule/inventory transitions, then lock the booking rows consistently. Exact inventory transfers and active booking counts must reconcile; fail closed on unexpected counters rather than treating least/greatest as reconciliation. Late confirmation after effective expiry returns the existing expired outcome and must not insert a paid receipt or decrement twice. Cancellation preserves the existing operational refund-pending marker and does not issue money or invent refund settlement.

5. Keep `rpc_expire_bus_holds` service-only; bound actual work/transaction duration as well as schedule count. Bind it to a named protected server scheduler/runner with an accountable owner, configured interval, recent-run outcome and lag/backlog alert. A migration/function grant or an idle test environment is not evidence of deployment. Diagnose nullable legacy holds instead of silently inventing expiry or releasing unknown paid evidence. Carry root's current recent-auth/verified identity/permission guards and original signatures/ACLs through every function rewrite.
