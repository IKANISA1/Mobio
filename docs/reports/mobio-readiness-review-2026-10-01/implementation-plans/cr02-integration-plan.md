Prepared 2026-10-01 from bounded read-only inspection after the tested server foundation. ## Outcome and available foundation

The submitted Mobio binary must let a store reviewer complete the declared passenger/driver tasks with coherent synthetic data, while its Auth identity cannot read or mutate production data, contact real users, change grants, confirm payments, access biometrics or register production push. Review credentials expire, rotate and revoke without waiting for an access JWT to expire.

`supabase/migrations/20261001193000_store_review_authority.sql` already supplies permanent private principal registration, disabled generation-controlled settings, fresh real-Auth-session leases, service-only registration/configure/status/revocation contracts, exclusion from both production identity helpers, ordinary PostgREST denial and restrictive public/standard Storage RLS. The unique local rehearsal applied 122 real migrations and passed 60 rolled-back actual-role SQL assertions; 89 application/standard Storage relations were guarded. Container and temporary workdir cleanup is verified in `cr02/run-99112/cleanup-verified.json`.

## Smallest complete server/auth integration

1. Add a new forward migration after the frozen foundation, owned by one backend agent. It extends `otp_codes_purpose_check` to `store_review` and adds explicit review principal/generation/role/challenge binding. All new columns remain service-only through the existing table privileges. Add a bounded configuration read RPC and exact service-only atomic review challenge claim using current settings/principal/generation/window and expected attempt/hash revision. Hold/recheck settings during the claim; later lease registration independently rechecks again, so a rotation between claim and Auth issuance produces no admitted session. Existing `claimOtpVerificationAttempt` remains the normal OTP contract. Do not edit historical migrations.
2. Configuration requires explicit `STORE_REVIEW_PHONE`, `STORE_REVIEW_OTP`, `STORE_REVIEW_USER_ID`, `STORE_REVIEW_GENERATION` and `STORE_REVIEW_SUPABASE_ORIGIN` (names proposed, values never public). Validate normalized phone/code/UUID/integer/exact configured `SUPABASE_URL` origin. Require a current independently enabled DB configuration with the same UUID/generation, supported fixture version and finite window. Missing/invalid/expired/disabled configuration admits no review shortcut. A selected/configured review phone must fail closed instead of falling through to ordinary delivery/session provisioning. Normal login can only succeed with its own freshly issued random challenge; a historical fixed code alone has no normal-login authority.
3. Move shared send limiter outside the review exemption: same `app_login` cap keys for review and ordinary sends, including resend 1/60 seconds, phone 5/hour, source 10/5 minutes and 30/hour, global 60/minute. Do not create a separate review global bucket that doubles production allowance. Review may use the approved store-access Play Integrity exception only after validated active review configuration; its rate and configuration checks are mandatory. Bind the code hash to purpose, phone, generation, principal, effective role and opaque challenge nonce using configured keyed hashing; no unhashed code, legacy hash or fixed-code OR fallback for review.
4. A new `_shared/store-review-session.ts` resolves only the explicitly configured preprovisioned Auth UUID. It requires permanent registration, nonanonymous/live/unbanned Auth, provider `store_review`, passenger/driver role and absent phone. Use an internal unguessable email and rotate its random password on the server; sign in through the anon Auth client with email/password, validate returned ID/provider/real JWT session ID, then call `rpc_register_store_review_session`. Do not call `ensureAppUserSession`, phone-owner provisioning, profile upsert, Admin grant paths or create a principal during login. If lease registration/status fails, return no client tokens and invalidate the newly issued session with a supported tested Auth revocation path; consumed challenge remains consumed. Never include tokens/code/password in logs or audit.
5. One registered driver review principal can support both passenger/driver UI modes without changing its server role: lease role remains the actual configured driver role and UI mode is synthetic presentation state. This fits the foundation's one configured principal and avoids per-login role mutation/parallel-session conflict. If store acceptance requires two independently authorized Auth roles, add an explicitly designed multi-principal settings contract first; do not silently reinterpret the singleton or factory role.
6. Add `store-review-session/index.ts` status/revoke operations. Validate the exact bearer through Auth, decode subject/session only after successful Auth validation, then invoke the service-only status RPC with those identities. Return only lease/fixture metadata with `Cache-Control: no-store`; no production rows or secrets. Revocation can revoke only the validated caller's lease and is idempotent. Status uses DB server time and requires exact provider/role/current registry/settings/session ownership; generation/disablement closes immediately. Do not permit client-selected UUID/session/role or raw decoded JWT to select a target.
7. Narrowly harden `_mobio_verified_phone_owner` to reject any permanent reviewer or `store_review` Auth provider before returning an ordinary phone owner; this protects both consumer/Admin service callers even after phone/provider tamper. Preserve installed owner/ACL/search path and ordinary/Admin positive cases. Add defense-in-depth provider rejection in `assertVerifiedPhoneUser`. The SQL rejection must be an error, not null, because null instructs callers to provision a new account. Guard installed `handle_new_user()` so new review-provider or permanently registered identities do not auto-create production profiles. Existing historical review accounts need separately approved readback/containment; do not auto-demote a potentially real phone owner.
8. Ordinary Edge provider admission must independently use permanent registry/database live authority. `requireAppUser()` can query `verified_app_user_id()` with the exact user bearer, and additionally require `verified_admin_user_id()` for stored provider `admin_whatsapp_otp`; this exercises the preserved ordinary pre-request hook, permanent registry and Admin idle/absolute lease. Recent authentication remains action-specific, not a global read gate. Fail closed on query errors/mismatched identity before creating/calling external provider clients. Service-role parameterized face RPCs additionally need target UUID/session registry exclusion: caller-bound `is_store_review_principal()` resolves the service subject there and is insufficient. `/root/admin_recent_auth` identified/owns the future CR11/12 plan for `mobio_private.require_verified_interactive_session(p_user_id uuid, p_session_id uuid, p_requires_recent boolean default false)`; coordinate one private helper/forward migration owner instead of duplicating it. Recipient eligibility separately excludes permanent review principals but must not require an enrolled recipient to be currently signed in.

## Client session and coherent synthetic data

Use one Supabase client/issuer and the existing real Auth restore/storage queue; no realm switch, separate artifact, release auth-bypass flag or weakened production `AccountSnapshot`. A stored review Auth token is transport material, not review authority.

Add a typed review identity kind to `StoredSessionIdentity` and permit `store_review` shape only for an explicitly typed login ticket. Preserve issuer/sub/session/anonymous validation, same-session-only refresh, native secure-store serialization, exit marker and stale completion fences. Keep `hasVerifiedSession/capture` restricted to ordinary production providers. Generalize only the common transport/commit fence enough to restore review tokens; completion must also have a current verified review status response bound to the exact restored user/session. Client-controlled send metadata alone never activates review.

Add `lib/core/auth/review_session_context.dart` and a small core status transport/lease model. Review authority requires accepted review transport, exact current Auth owner/session, supported fixture version, no exit/storage/login quarantine, and successful authenticated status. Derive a monotonic expiry deadline from `{server_now, expires_at}` rather than trusting the wall clock. Revalidate at cold resume, foreground resume and before review task mutations; periodic bounded status refresh enables prompt revocation visibility while open. Expiry/status error/background/resume invalidates review synchronously, cancels owned native work and clears fixture state; no offline mutation while status is unavailable. Production data remains blocked server-side even before client observes revocation. Never persist synthetic data or a reusable trusted lease in prefs; secure persisted Auth is revalidated before a new synthetic state mounts.

Add `lib/features/store_review/domain/store_review_state.dart` for fixture records/pure mutation rules and `application/store_review_controller.dart` for session-owned state. Bind state to issuer, user, session, generation, fixture version and a local revision. Pure records use shared model contracts or plain fixture records, not feature-data/platform classes; adapt to existing feature models at feature boundaries. Feature data must not import application/presentation; inject narrow repository interfaces from domain into review adapters. Core does not import features. Preserve `docs/architecture/README.md` direction and structure checks.

The controller is the single source for a synthetic profile with valid UUID/6-digit member ID, Rwanda default, driver vehicle, two synthetic peers, catalog/place fixtures, scheduled posts, conversations/messages/report/block state, consent/favorite addresses and in-app notifications. Explicitly strip contact/receiving/provider identifiers and external avatar/media URLs. Use local assets and generated fixture UUIDs; fixture names/IDs cannot select production rows. Mutation rules validate current lease/revision and ownership and return canonical models used by existing widgets. New posts appear on Home/Bookings/Details, edits update all three, cancellation consistently removes/labels them; local conversations/messages/unread/block/report states remain coherent. Logout/expiry/new session resets all state, location and pending mutations. The UI must identify synthetic review data using Mobio's existing design system and sole Revolut authority.
