## Confirmed findings and evidence gaps

### UX-01 — High: published Terms contradict the actual authentication contract

**Confirmed content defect.** [landing/terms-and-conditions.html:99–103](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/landing/terms-and-conditions.html:99) says Mobio automatically creates an anonymous account and phone/name are never mandatory. Current [landing/index.html:171–172](/Volumes/PRO-G40/Projects/Recovered-G-PRO/Mobio/landing/index.html:171) instructs WhatsApp sign-in; AGENTS and router guards require verified WhatsApp OTP for protected work and reserve anonymous sessions for bootstrap. Users are accepting an inaccurate account description, and support/store review receive conflicting instructions. The Terms' May 2026 date and service description also predate approved BioPay expansion.

**Recommendation/owner:** Product/legal content owner updates the actual published Terms and harmonizes developer legal identity, current verified authentication, enabled BioPay/provider boundaries, subscriptions/tokens where present, public transport availability and data rights. Do not convert that content task into an auth redesign. **Closure:** legal owner review, automated assertions for the obsolete anonymous-account copy, deployed page readback and links/consent journey checked against the exact release.

### UX-02 — High: admin search/filter results can become stale under out-of-order responses

**Confirmed code-path defect; live reproduction not run.** `admin_reports_screen.dart:59–86` publishes results based only on account/mounted validity; search starts a request on every keystroke at `:512–517`. Changing status at `:535–540` and page at `:612–614` starts overlapping requests. `admin_trips_screen.dart:63–92` has the same loader pattern; search at `:277–282` reloads silently. There is no request revision or query snapshot comparison. Request A can return after request B and replace the results for B while the filter/search still displays B. Account fencing prevents a different class of stale response and does not solve this within-account race.

**Impact:** operational queues can show records unrelated to the visible filter, including resolved reports under Open, and operators may act using stale context. **Recommendation/owner:** admin/application owner reuses the existing request-version strategy in `admin_users_provider.dart:61–106` or audit-log revision guard (`admin_audit_log_screen.dart:243–269`), with bounded debounce where useful. Snapshot filters/page, fence stale success and errors, retain account fencing. **Closure:** controlled delayed A/B responses prove latest-query results and counters survive older success/failure; test search-clear, rapid filters and page changes, then one exact-build admin browser journey.

### UX-03 — High: bulk role promotion has no review of recipients and privilege effect

**Confirmed interaction path.** `admin_user_bulk_actions.dart:37–43` makes Admin an immediate action. `admin_users_screen.dart:168–171` invokes `applyRoleToSelected` directly. `admin_users_provider.dart:275–304` derives selected targets and issues parallel role RPCs. The existing code excludes the current operator, skips no-op roles, disables competing updates and reports partial failures; retain those protections. No review/confirm step or undo is present in this path.

**Impact:** an inadvertent click or misunderstanding changes multiple users' access authority. This is a usability/error-prevention finding, not a claim that backend authorization is missing. **Recommendation/owner:** admin/product owner adds a focused review of named target accounts, current/new role, exact eligible/skipped count and privilege consequence before committing admin promotion or bulk demotion. Preserve the already functioning partial-failure reconciliation; give failed accounts an explicit retry path. **Closure:** Cancel makes zero writes; confirm targets only the reviewed snapshot; stale selection/account change invalidates commit; mixed failures retain truthful counts; keyboard/reader users can review before commit.

### UX-04 — Medium: directory sort is page-local while the UI reads as a directory-wide order

**Confirmed contract mismatch.** `admin_user_service.dart:10–24` accepts role/search/limit/offset without a sort parameter. `admin_users_provider.dart:32–39` truncates the server page and then sorts it; `:119–123` resorts only the current page. The UI exposes Name A–Z, Name Z–A, Role, Newest and Online first at `admin_users_screen.dart:296–323`. Thus the earliest global name/newest user may be on another page even after selecting that order.

**Recommendation/owner:** backend/admin owner applies a whitelisted sort and stable tie-breaker before pagination in the server contract, or accurately labels the existing feature as sorting this page if that is the approved behavior. **Closure:** a two-page fixture with interleaved names/dates verifies monotonic ordering and deterministic page boundaries after filters; no duplicated/missing users under equal sort values.

### UX-05 — Medium: a pagination lower bound is presented as the exact member count

**Confirmed information defect.** `admin_users_state.dart:82–83` computes `page * rowsPerPage + users.length + (hasNextPage ? 1 : 0)`. It is a known lower bound when another page exists. `admin_users_screen.dart:290–291` renders it as “N matching members.” With 1,000 matching accounts, the first 25-row page can say 26 matching members. Reports similarly derive pagination totals at `admin_reports_screen.dart:359–360`; do not reuse those estimates for platform queue KPIs.

**Recommendation/owner:** admin/data owner returns an exact filtered count where justified, or labels the quantity as “at least N” / visible rows with next-page navigation. **Closure:** >2-page datasets show truthful count labels throughout navigation; platform/visible-row metrics remain distinguished.

## Research-backed acceptance standards

For web/PWA/admin/website, assess applicable WCAG 2.2 A/AA complete pages/processes: normal text 4.5:1, qualifying large text 3:1, essential non-text identification 3:1, keyboard/focus not obscured, stable labels/status announcements, 200% text and 320 CSS-px equivalent reflow, and accessible authentication assistance. Minimum pointer targets use 24×24 CSS px or a justified exception. Automated scans and screenshots alone do not prove conformance. Source fidelity cannot justify preserving an accessibility defect. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

For Flutter, validate actual TalkBack/VoiceOver tasks and semantic name/role/value, inspect text at large scale and use Flutter's meaningful accessibility guidance/tests within the existing framework. A Semantics wrapper is supporting implementation, not a speech-result certificate. [Flutter accessibility guidance](https://docs.flutter.dev/ui/accessibility-and-internationalization/accessibility).

Play expects both a discoverable in-app deletion path and an external functional deletion resource for apps that create accounts; the web resource may provide an email pathway. The existing source has both pathways, but enabled intake and actual downstream deletion are still unverified. [Google Play account-deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).

Apple permits manual deletion but ordinarily requires app-initiated deletion rather than forcing email/support; the highly regulated exemption needs a demonstrated basis. Disabled intake with an email-only fallback therefore needs resolution before an iOS release claim. Confirm deletion completion and retention disclosure separately from request intake. [Apple account-deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

Use field web benchmarks LCP ≤2.5 s, INP ≤200 ms and CLS ≤0.1 at the 75th percentile with date window/device segment. A single local lab run would diagnose, not prove field performance; choose device/network and native startup/scroll budgets for Mobio's actual users. [Core Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds).

Public website discoverability should use useful crawlable content/links and descriptive titles/snippets; verify actual production indexing eligibility. Metadata changes cannot promise ranking. [Google Search starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide).
