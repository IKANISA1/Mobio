## Substantive contract findings

| ID | Finding and evidence | Disposition |
| --- | --- | --- |
| SR-01 · high | In the imported Android SMS bridge, `DurableSmsQueue.enqueue` increments `blocked` and skips an eligible SMS when the active row/byte limits are reached. `SmsReceiver.onReceive` logs the blocked count and schedules a normal upload, but does not persist the rejected message or its hash. A search of the bridge source found no OS inbox rescan or other retry path for that rejected SMS. The runbook says a full queue requires retention/retry; the implementation currently relies on manual reconciliation outside this queue. This is a source-level omission risk when the collector is saturated, independent of whether the OS SMS app retains the original message. | **Collector activation remains blocked** until a reviewed durable overflow/recovery method and saturated-device test demonstrate that eligible receipts can be reconciled without silently dropping the collector's only copy. Preserve the original SMS and queue during any incident. Do not enable automatic allocation as a workaround. |
| SR-02 · medium | `supabase/hardening/2026-09-28/README.md` still says “seven versioned SQL bodies” and its numbered description stops at body 07. The actual manifest has **12 bodies**, and the read-only preparation plan reports **12 planned, zero installed, `database_applied:false`**. Bodies 08–12 cover admin leases, wallet operations, chat, push and privacy, so the README understates the required ordered installation. | Treat the manifest and increment 05–09 runbooks as the source list. Correct the README during the next package-lineage source revision; retain the exact imported package bytes in this review. No SQL was applied. |
| SR-03 · release gate | The integrated session, wallet, chat, push and privacy code uses owner/session checks, idempotency or durable status protocols, and explicit default-off database policies. Those safeguards were traced through the client/Edge/SQL source, but no linked PostgreSQL/Auth/provider/device acceptance was produced here. The privacy runbook explicitly says requests/evidence recording do not execute cross-provider erasure. | Keep these as source candidates. A request receipt, wallet/chat acknowledgement, FCM provider acceptance or local file hash must not be reported as a completed payment, delivered device notification or completed account deletion. |

For SR-01, the exact source path is `apps/momobio_sms_bridge/app/src/main/java/com/momobio/app/DurableSmsQueue.kt` (`enqueue`) and the receiver is `apps/momobio_sms_bridge/app/src/main/java/com/momobio/app/SmsReceiver.kt` (`onReceive`). The published runbook is `docs/production-readiness/INCREMENT04_SMS_INTAKE.md`, especially its full-queue note. The code exposes an attention counter and notification; that is visible operational evidence of blockage, not a saved retryable receipt. The issue is recorded here rather than changing the package-exact application source without an accepted queue design and device test.
